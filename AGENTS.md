# AGENTS.md

## Назначение проекта

Finance — локальное desktop-приложение для управления личными финансами:
доходами, расходами, счетами, категориями, бюджетами и финансовой аналитикой.
Приоритеты: точность расчетов, сохранность данных, приватность и простой UX.

## Технологии

- Tauri 2 и Rust — desktop-оболочка и системная логика.
- React 19, TypeScript и Vite — интерфейс.
- SQLite через `tauri-plugin-sql` — локальное хранение данных.
- Основной URL базы: `sqlite:finance.db`.

## Структура

- `src/` — React-интерфейс и клиентская бизнес-логика.
- `src/db.ts` — единственная точка доступа frontend-кода к SQLite.
- `src-tauri/src/` — Rust-код и регистрация Tauri-плагинов.
- `src-tauri/src/lib.rs` — SQLite-миграции и запуск приложения.
- `src-tauri/capabilities/` — минимально необходимые разрешения Tauri.

## Правила предметной области

- Денежные значения хранить целыми числами в минимальных единицах валюты
  (`amount_minor`: тиыны/копейки/центы), а не `REAL`.
- Валюту хранить отдельным ISO 4217 кодом (`KZT`, `USD`, `EUR`).
- Не складывать суммы разных валют без явно заданного курса конвертации.
- Доходы представлять положительной суммой, расходы — отрицательной.
- Перевод между счетами создавать атомарно как две связанные операции.
- Даты хранить в UTC в ISO 8601; локализовать только при отображении.
- Балансы и итоги вычислять из операций, не дублировать без необходимости.
- Для финансовых расчетов не использовать арифметику JavaScript `number`
  над дробными денежными значениями.
- Удаление счета или категории не должно незаметно удалять историю операций.

Текущая таблица `transactions` использует `amount REAL`; при развитии схемы
перевести ее отдельной миграцией на целочисленный `amount_minor`.

## Планирование личного бюджета

- Приложение рассчитано на одного человека и один локальный профиль.
- Не добавлять регистрацию, роли, семьи, команды и совместный доступ.
- Бюджет создается на календарный месяц и на календарный год в выбранной основной валюте.
- Пользователь задает планируемый доход и лимиты расходов по категориям.
- Фактические расходы и доходы рассчитываются из операций за период.
- Для каждой категории показывать план, факт, остаток и процент использования.
- Общий остаток считать как `плановый доход − лимиты расходов`.
- Свободные средства показывать отдельно от уже распределенных по категориям.
- Годовой план хранить отдельно от месячных; не смешивать периоды в одной записи.
- Разложение годового бюджета на 12 месяцев — только явное действие пользователя.
- При разложении делить суммы целочисленно; остаток от деления распределять по первым месяцам.
- Предупреждать при достижении лимита и перерасходе, но не запрещать операцию.
- Изменение бюджета не должно изменять или удалять реальные операции.
- Копирование бюджета на следующий месяц или год должно быть явным действием.
- Перенос неиспользованного остатка между месяцами и годами по умолчанию выключен.
- Исторические бюджеты сохранять для сравнения плана с фактом.
- Поддерживать категории обязательных и необязательных расходов.
- В прогнозе учитывать регулярные доходы и расходы, не создавая фактические
  операции до наступления даты.

## SQLite и миграции

- Все изменения схемы оформлять последовательными версионированными миграциями.
- Никогда не изменять уже выпущенную миграцию; добавлять новую.
- Использовать параметры запросов (`$1`, `$2`), не собирать SQL из строк.
- Связанные записи изменять внутри транзакции SQLite.
- Включать foreign keys и создавать индексы для полей фильтрации и связей.
- Перед удалением или изменением данных проверять влияние на финансовую историю.
- Методы работы с БД должны возвращать типизированные модели и понятные ошибки.

## TypeScript и React

- TypeScript держать в строгом режиме; не использовать `any` без обоснования.
- Использовать функциональные компоненты и хуки.
- Компоненты отвечают за отображение, операции с БД находятся в `src/db.ts`
  или специализированных repository/service-модулях.
- Валидировать пользовательский ввод до записи в БД.
- Для асинхронных действий показывать состояния loading, empty и error.
- Форматировать деньги через `Intl.NumberFormat` с валютой операции.
- Интерфейс и тексты должны быть пригодны для локализации.
- Не блокировать интерфейс длительными вычислениями.

## Rust и Tauri

- Держать Tauri capabilities минимальными; не добавлять широкие разрешения.
- Системную, чувствительную и требующую доверия логику выполнять в Rust.
- Не использовать `unwrap()`/`expect()` в рабочей логике, кроме фатального
  запуска приложения; ошибки возвращать с контекстом.
- Не открывать внешние URL и файлы без явного действия пользователя.

## Приватность и безопасность

- Финансовые данные по умолчанию остаются локальными.
- Не логировать суммы, названия операций, номера счетов и персональные данные.
- Не хранить секреты, токены и пароли в репозитории или обычном SQLite-тексте.
- Для секретов использовать системное защищенное хранилище.
- Импортируемые файлы считать недоверенными: проверять формат, размер и значения.
- Экспорт и резервное копирование выполнять только по явному запросу пользователя.

## Проверка изменений

После изменений запускать соразмерные проверки:

```bash
npm run build
cargo check --manifest-path src-tauri/Cargo.toml
```

Для финансовой логики добавлять тесты как минимум на:

- доходы, расходы, нулевые и крупные суммы;
- округление и форматирование валют;
- переводы между счетами и атомарность;
- разные валюты и даты/часовые пояса;
- расчет месячного бюджета, остатка, перерасхода и план/факт;
- расчет годового бюджета и разложение на месяцы без потери остатка;
- отсутствие влияния изменений бюджета на фактические операции;
- миграции существующей базы без потери данных.

## Рабочий процесс агента

- Сначала изучить текущую схему и затронутые потоки данных.
- Делать минимальное изменение в рамках запроса, без несвязанного рефакторинга.
- Не удалять и не перезаписывать пользовательские финансовые данные.
- При неоднозначности, способной изменить деньги или данные, задать вопрос.
- После изменения схемы объяснить миграцию и риск для существующих данных.
- Не добавлять зависимости без необходимости; выбирать поддерживаемые библиотеки.
- Не создавать git-коммиты и не выполнять push без явного запроса.
